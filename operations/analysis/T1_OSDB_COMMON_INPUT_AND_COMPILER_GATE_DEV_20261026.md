## 实际编译检查的结论

对四份schema直接调用当前适配分支`schema_services.py`，使用固定、与题目答案无关的开发计划；executor是禁止派发的哨兵，没有数据库执行。

1. 两输入Actor.entity_id集合差计划在派发前被拒绝，原因是Neo4j默认分支仍要求投影eid。当前TuGraph的原生主键支持没有自动适用于Neo4j的OSDB投影。
2. 同一实际schema中不存在Actor.eid，旧Neo4j元数据注入却允许编译该属性。不能把entity_id随意改名为eid来绕过，或者由空属性结果冒正确执行。
3. 对STRING类型source_event_time的比较会原样编成字符串比较，不插入datetime。固定合成UTC例子`...00Z`早于`...00.1Z`，字符串次序却相反，说明该通用时间合同不能直接沿用。
4. 四叶选择计划因最多两调用限制在派发前拒绝。按Issue/PR和早/晚窗口展开的直接构造会遇到此限制；**这不是四个候选均不可表达或覆盖率0的证明**。通用多类型视图可能改变所需调用数，但其语义与权限尚未准入，不能根据这次检查替方法删题。

时间反例另做了真实数据核对：全部634,665条source_event_time均为UTC整秒字符串，与原候选三个固定整秒边界的逐值比较中，字符串与时间瞬间次序差异为0。因此本批没有观测到该时间次序错误；通用分数秒反例不能算当前题目错答。其余时间字面量、聚合和未来输入仍需显式合同。上述检查均不是模型EX、任务完整表达性分析或编译器已修复的声明。

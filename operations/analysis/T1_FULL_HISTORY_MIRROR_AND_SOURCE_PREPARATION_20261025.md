## 账本如何保持一致

1. 副本保留历史槽位的原字节，包括原请求路径、哈希、失败和未知 usage。
2. 映射只在运行或分析的文件访问层生效。我们不修改历史 JSON。
3. 每个原请求目录映射到较短的副本目录。这样可避开 Windows 长路径限制。
4. 完整副本由原计数器检查。累计数必须仍为 3,266，上限必须仍为 12,000，pending 必须为 0。
5. 正式交接时，再锁住旧写入端，固定新快照并核对远端 owner。当前只是只读草稿副本，没有转交执行权。

在 Windows 的合成检查中，新请求目录的映射必须先于历史映射。历史目录之间必须按最长前缀匹配，不能直接采用清单的原始排列顺序；候选 open_clone 已实施该排序。原记录仍保留原路径。Linux 的新请求也须按明确的运行根目录登记，供回传分析使用。

## 镜像检查覆盖什么

| 检查 | 要阻止的问题 |
|---|---|
| 原槽位和计数保留 | 把历史额度归零，或修改已有尝试 |
| 重复同步 | 同一次尝试被重复计数；同字节同步允许重复确认 |
| 累计额度 | 新增失败也占额度，达到上限后不再预留 |
| 未知请求 | 缺少 terminal 时不导出为完成，也不重发 |
| 缺文件、文件被改 | 不先写入新的账本指针 |
| 目标已有不同内容 | 拒绝覆盖，保留冲突供检查 |
| 旧 C 盘路径 | 在副本中定位文件，原槽位不改写 |
| Windows 过长目标路径 | 提前拒绝，要求更短准备目录 |

这些检查使用隔离的本地合成文件。它们没有调用模型或数据库，也不构成远端运行效果或 T4 效率结果。镜像工具只处理尝试证据；完整预测、评分与成本文件的最终回传还须验收。

## 发现并修正的准备问题

首次本地复制采用完整嵌套路径，触发 Windows 路径长度限制。随后确认 Python 3.9 的 Path.resolve 会去掉扩展路径前缀，导致原计数器无法访问过长副本。我们改为较短的目录映射，并增加提前拒绝过长根目录的检查。原冻结计数器没有改动。

全量副本检查另发现：祖先目录映射先匹配时，可能遮住更具体的子目录。我们在候选文件访问层固定最长前缀优先，并增加嵌套目录检查。已有副本的账本、请求、terminal 和清单不重写；只重新核验原字节及正确的映射行为。这些都是准备阶段发现的问题，未触发任何模型请求。

失败草稿 full_history 和旧 full_history_v2 留在本地，不是可运行账本。旧 v2 复制辅助进程在确认 PID 和命令后停止，没有停止任何正式 runner、数据库或 GPU 服务。当前候选为 full_history_v3，只有报告通过的版本才可用于后续准备。

# 接口复核：当前可用，编码不是这批失败的解释

我之前把“实验中有间歇失败”说成“接口仍未修复”，判断过早。现有记录不足以要求重启或修复服务端。

| 检查 | 结果 |
|---|---|
| 历史 75 次失败请求 | 消息中均没有汉字 |
| 历史请求的发送格式重建 | ASCII JSON；UTF-8 解码后与原请求一致 |
| 完整历史失败请求，经过本机代理 | 2/2 成功 |
| 同一完整请求，直连 | 2/2 成功 |
| 完整请求改用 `high` | 成功；原 `low` 也成功 |
| 中文使用 `\uXXXX` 转义 | 成功 |
| 相同中文使用 UTF-8 原文 | 成功 |
| Python 与 curl | 均成功 |

本轮 10 次调用全部成功。不能把代理、`low` 或中文编码写成已确认原因。之前的 HTTP 500 和超时是真实记录；为什么当时失败，目前仍未确定。

诊断单列记账：新增 10 次调用、23,274 个已知 token。累计 334/1,200 次，75 次用量未知。诊断结果不替换论文实验的原始预测。

我们继续运行已冻结的新任务。后续批次会明确记录网络路由，保留原模型参数、题目、评分和连续 3 次接口失败即停止的规则。

补充：随后启动的新任务首轮 3 个请求都返回 HTTP 500，已按规则停止。它们均没有汉字，JSON 编码正确，且已验证走直连。因此，“中文编码导致失败”没有证据支持，“绕过代理就能解决”也不成立。当前应描述为：这 10 项诊断可用，但新的正式请求仍会失败，根因尚未确定。
